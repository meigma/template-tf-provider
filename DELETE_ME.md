# Welcome to the Meigma Terraform Provider Template

This repository was generated from `template-tf-provider`, the standard starter
for Meigma Terraform providers. It arrives as a working provider: a worked
example resource and data source, a pinned toolchain, documentation that builds
for both provider registries and a docs site, and a release pipeline that has
already been exercised in the template repository.

Delete this file once you finish the checklist below. It exists only to orient
the first owner of the new repository.

## What This Template Provides

- A [Plugin Framework](https://developer.hashicorp.com/terraform/plugin/framework)
  provider whose `main` package is at the repository root, the layout
  HashiCorp's own scaffolding uses.
- A worked `example_item` resource and data source with create, read, update,
  delete, and import, split across three packages: `internal/core` holds the
  domain and a `Store` port, `internal/client` implements that port against a
  JSON file, and `internal/provider` is the Terraform adapter. Dependencies
  point inward; only the adapters touch the outside world.
- Mocks generated by `mockery` and checked in under `internal/core/mocks`, so
  `go test` works without running a generator first.
- Four test layers: domain unit tests, adapter tests against a real file,
  provider tests against the generated mock, and acceptance tests that drive a
  real Terraform-compatible CLI.
- A `mise`-pinned toolchain (`mise.toml` + `mise.lock`) and Moon tasks for
  `format`, `lint`, `build`, `test`, `testacc`, the docs pipeline, and the
  aggregate `check`.
- One `docs/` tree with two consumers: `tfplugindocs` generates the registry
  reference pages from the provider schema, and MkDocs builds the same tree
  plus the hand-written pages into a site. CI fails if the generated pages
  drift from the schema.
- A release pipeline that produces exactly what the Terraform and OpenTofu
  registries ingest — 13 platform zips, the manifest copy, `SHA256SUMS`, and a
  detached GPG signature — plus SBOMs, a cosign bundle, and isolated build
  provenance. Release Please opens the release PR and creates a draft release;
  the draft goes public only after every check passes.
- A dry-run workflow that rehearses the whole release path, signing included,
  on every release pull request.
- `scripts/gpg-provision.sh` to create the release signing key, and
  `.github/repository-settings.toml` plus
  `.github/scripts/configure_github_repo.py` to apply repository settings.
- Pinned CI, Dependabot coverage, and a manually dispatched acceptance-test
  workflow.

## How It Works

Moon is the entry point for local development and CI:

```sh
moon run root:check
```

That aggregate runs the formatter, linter, build, unit tests, the release
script tests, the docs drift check, the registry docs validation, and the
MkDocs build. CI runs the same path through `moon ci --summary minimal`.

Every task runs against binaries `mise` puts on `PATH`; Moon manages no
toolchain of its own. Run `mise install` once after cloning.

Acceptance tests are deliberately outside all of that. They start a real CLI
and run plan, apply, import, and destroy, so nothing triggers them
automatically — not `moon ci`, not a pull request, not a schedule.

The release machinery is enabled in the template repository on purpose: the
example provider proves the whole path, including GPG signing and the registry
contract checks, before a generated project inherits it.

## First Setup Checklist

Work through these in order. Steps 1 and 2 change the code; steps 3 to 6 are
one-time repository setup that must be finished before the first release.

### 1. Rename the module and the provider

Pick two names first:

- the **provider name**, which is also the repository name and the binary name:
  `terraform-provider-<name>`, all lowercase
- the **type name**, the same `<name>` without the prefix — the token that
  prefixes every resource, as `example` does in `example_item`

Rename the module:

```sh
go mod edit -module github.com/meigma/terraform-provider-YOUR_NAME
```

Then update the import paths in every `.go` file, and these places that hold
the old names literally:

| File | What to change |
|------|----------------|
| `.mockery.yml` | the `packages:` key, which is a module path |
| `.golangci.yml` | `goimports.local-prefixes` |
| `main.go` | the `address` constant, `registry.terraform.io/NAMESPACE/TYPE_NAME` |
| `doc.go` | the command name in the package comment |
| `internal/provider/provider.go` | `TypeName` |
| `internal/provider/acceptance_test.go` | `providerNamespace` |
| `.goreleaser.yaml` | `project_name`, the build `id`, the archive `id` and its `ids` entry |
| `moon.yml` | the `build` task's `-o bin/…` and its `outputs`, and the `--provider-name` flag in `docs-gen`, `docs-check`, and `docs-validate` |
| `release-please-config.json` | `package-name` |
| `scripts/*.sh` | the `PROJECT` constant in all four scripts, and the contract comment block at the top of `check-release-contract.sh` |
| `.github/workflows/release.yml` | the `SHA256SUMS` asset paths and the verification commands in the release summary |
| `.github/workflows/attest.yml` | the asset name in the input's description |
| `mkdocs.yml` | `site_name`, `site_description`, `site_url`, `repo_name`, `repo_url` |
| `README.md`, `CONTRIBUTING.md` | the project description, the binary path, and the verification commands |
| `examples/`, `templates/index.md.tmpl` | the directory names under `examples/` and the prose in the template |

`.github/workflows/release-dry-run.yml` needs no edit: it gets every asset name
from the scripts.

Sweep for anything left over:

```sh
rg --hidden --glob '!.git' \
  'terraform-provider-example|meigma/example|example_item|EXAMPLE_STORE_PATH'
```

Everything that survives is either a page under `docs/`, which step 2 deals
with, or a real miss.

Finish with:

```sh
go mod tidy
moon run root:build
```

### 2. Replace the example resource

`example_item` is a worked example meant to be thrown away. Keep the seam, not
the item.

- Rewrite `internal/core`: your domain type, its validation rules, and the port
  the provider depends on. Keep it free of Terraform types and I/O — that is
  what makes it testable without side effects.
- Rewrite `internal/client` to implement the port against whatever the provider
  actually talks to. A JSON file becomes an HTTP client; the shape does not
  change.
- Rewrite `internal/provider` to map configuration, plan, and state onto the
  domain, and domain errors back onto attribute paths.
- Regenerate the mocks after changing the port: `mise exec -- mockery`.
- Update all four test layers alongside the code. Do not delete the acceptance
  tests; they are the only thing that proves the provider works against a real
  CLI.
- Replace the configurations under `examples/` and the prose in
  `templates/index.md.tmpl`. `tfplugindocs` embeds both in the reference pages.

[How this provider is structured](docs/explanation/architecture.md) explains the
split and the rule that trips people up: a provider may not silently rewrite a
value the user configured.

Regenerate the registry reference pages and commit the result:

```sh
moon run root:docs-gen
```

Never hand-edit `docs/index.md`, `docs/resources/`, or `docs/data-sources/`.
`moon run root:check` regenerates them into a scratch directory and fails when
the committed copies differ.

Then rewrite the hand-written pages under `docs/tutorials/`, `docs/how-to/`,
and `docs/explanation/`, which still describe `example_item`, and update
`mkdocs.yml`'s `nav` to match.

### 3. Apply the repository settings

```sh
uv run .github/scripts/configure_github_repo.py plan  --repo meigma/YOUR_REPO
uv run .github/scripts/configure_github_repo.py apply --repo meigma/YOUR_REPO
```

Review the plan before applying. `.github/repository-settings.toml` sets signed
commits, squash-only merges, protected tags, immutable releases, private
vulnerability reporting, and the required status checks. Set `is_template` to
`false` in that file for a generated repository, and adjust the required check
contexts only if you rename a workflow job.

The script reports settings GitHub does not expose through its API as manual
follow-ups. Apply those by hand.

### 4. Provide the Release Please app credentials

The Release Please workflow authenticates as a GitHub App, because tags are
protected and the default token cannot create them. Set both on the repository
before the first release:

- the `MEIGMA_RELEASE_APP_ID` repository **variable**
- the `MEIGMA_RELEASE_APP_PRIVATE_KEY` repository **secret**

The tag ruleset in `.github/repository-settings.toml` already grants the
`meigma-release-please` app a tag-creation bypass. Without the credentials the
workflow fails at its first step and no release PR is ever opened.

### 5. Provision the release signing key

```sh
scripts/gpg-provision.sh
```

This creates the signing key, stores it in the `GPG_PRIVATE_KEY` and
`GPG_PASSPHRASE` Actions secrets, and prints the public key. Register that
public key with both registries **before** publishing anything: a release
neither registry can verify is rejected, and fixing the key afterwards does not
make them re-ingest it.

[How to publish the provider to the registries](docs/how-to/publish.md) covers
the key registration and the one-time listing in each registry, end to end.

### 6. Reset the release state and enable verifiable builds

- Truncate `CHANGELOG.md` to an empty file and set
  `.release-please-manifest.json` back to `{".": "0.0.0"}`. Both carry the
  template's release history, which is not yours. Leave the file genuinely
  empty: Release Please writes its own `# Changelog` header, and a heading you
  leave behind is demoted to a stray `## Changelog` under the first entry.
- `0.0.0` is Release Please's "never released" sentinel, not a version it will
  bump from. With no matching tag it ignores the manifest entirely and cuts the
  first release at `initial-version` in `release-please-config.json`, which this
  template sets to `0.1.0`. Change that if a generated provider should start
  somewhere else; the `bump-*-pre-major` settings only take effect from the
  second release onward.
- Turn on `gomod.proxy` in `.goreleaser.yaml` once the module path matches the
  repository's real public URL. The comment above `builds:` explains why it is
  off in the template and what to check when you enable it.

### 7. Know what to expect from the acceptance tests

They pass on the untouched template and break the moment you start replacing
`example_item`, because every assertion in them names it. That is expected and
blocks nothing: no workflow, schedule, or pull request runs them, so the suite
stays red until you rewrite it alongside the real resource. Do rewrite it — it
is the only test layer that proves the provider works against a real CLI.

Run them yourself with:

```sh
moon run root:testacc                                  # the pinned OpenTofu
TF_ACC_TERRAFORM_PATH=$(mise which terraform) \
  moon run root:testacc                                # the pinned Terraform
```

Or dispatch the **Acceptance Tests** workflow from the Actions tab; its `cli`
input runs `tofu`, `terraform`, or both.

One gotcha: the task is marked `runInCI: false`, and Moon filters it out
whenever `CI` is set in the environment — including for an explicit
`moon run root:testacc`. If you export `CI` locally, the run fails with "No
tasks found" rather than skipping quietly. Unset it, or run the task through
`env -u CI`.

### 8. Finish the repository docs

- Rewrite `README.md` for the actual provider.
- Review `CONTRIBUTING.md` and `SECURITY.md`. `SECURITY.md` is a placeholder
  and says so; replace it with a real policy.
- Add a license before making the repository public.

### 9. Check, then delete this file

```sh
moon run root:check
rm DELETE_ME.md
```
